# A1: Dynamic Requirements Analysis

The A1 Requirements Analyst is integrated into `agentic_web_collaborative` for natural-language inputs. It analyzes the request, saves an existing-schema canonical manifest and continues through the existing candidate-generation stages when ready. Manifest inputs bypass reanalysis. The standalone `intake` CLI remains available for preparing reusable specifications independently of candidate generation. Both paths use the same analysis implementation, existing LM Studio client and validation. The baseline graph, placement policy and verifier remain unchanged.

```powershell
python -m agentic_web intake `
  --prompt "Generate a professional personal website from my resume." `
  --output tasks/generated/personal_site.json
```

Supporting material can be supplied as plain text using `--context`. The command does not read or extract resume documents. Without requested source material, the analyst must record a blocking missing-information question instead of inventing its contents.

```powershell
python -m agentic_web intake `
  --prompt "Build a website that displays the heading 'Community Notice'." `
  --output tasks/generated/notice.json `
  --model google/gemma-4-e4b `
  --seed 1025
```

The CLI prints `status`, the canonical `output_file`, an `analysis_file`, the artifact `run_dir`, source/task hashes and `ready_for_generation`. Successful analysis returns exit code 0, including `needs_review`; failed inference or validation returns 1. Invalid CLI/model configuration returns 2. `needs_review` means blocking missing information/ambiguities or unsupported runtime needs remain. It is a valid analysis result, not permission to invent missing information.

Inspect the saved analysis before using the canonical task for candidate generation:

```powershell
Get-Content tasks/generated/notice.json
# Use the analysis_file path printed by intake to inspect traceability/questions.
python -m agentic_web validate --task tasks/generated/notice.json
python -m agentic_web generate --task tasks/generated/notice.json --output runs
python -m agentic_web generate --task tasks/generated/notice.json --workflow collaborative --output runs
```

Multiple generation runs reuse the same manifest and task hash; they do not rerun analysis. Existing output files are never overwritten. Resolve missing inputs by supplying a revised request/context to a new output path; there is no automatic clarification loop or repair. The readiness flag is advisory metadata for inspection; the existing generation command remains responsible for runtime/contract validation and deterministic acceptance.

## Interactive testing in LangGraph Studio

Run `langgraph dev` in the `agentic-web` environment from this repository and select **agentic_web_collaborative** in Studio. Use a new thread for each independent request. Natural-language input follows:

```text
START -> requirements_analyst -> task_loader -> planner
      -> [ux_agent, architecture_agent] -> coordinator -> implementer
      -> verifier -> qa_critic -> acceptance_gate -> END
```

Existing `task_path`/`task_spec` inputs go directly to `task_loader`. A blocked, invalid or unsupported analysis ends before planning/generation. Set `analyze_only: true` to inspect a ready specification without starting candidate generation in the same collaborative graph.

Example Studio input:

```json
{
  "prompt": "Generate a professional personal website from my resume.",
  "output_root": "runs",
  "model_config": {
    "model": "google/gemma-4-e4b",
    "seed": 1025
  }
}
```

Add `supporting_context` with actual plain text when available; the resume example will stop for review if the resume is missing. Studio input needs `prompt`, not a task manifest. The graph also analyzes the existing `requirements` input when no manifest is supplied. The output state contains the validated `task_spec` and complete `analysis`, so provenance, questions, readiness and metrics can be inspected directly in Studio. The graph saves a unique canonical manifest under `output_root/intake_tasks` and returns its `canonical_task_file`; optionally specify a new `task_output_file` path. Subsequent independent experiments can reuse that file through `task_path` without reanalysis. Existing files remain protected. For JSON/API input, optional analyst caps use `model_config.planner_max_tokens`; the Analyst uses the existing Planner model assignment.

When `resource_config` is supplied, analysis uses the existing placement scheduler and Planner lease in an intake resource session. Its owned instances are released when that stage finishes; external/manual instances stay protected. Candidate generation then uses its existing resource session and final cleanup. Analysis artifacts live under `intake_run_dir`, and candidate artifacts include a copy of `requirements_analysis.json` plus links back to the source analysis.

## Analysis contract

The analyst's structured response reuses the existing task, feature, runtime, verification and test field definitions. Each functional/nonfunctional entry contains its own tests and `traceability` record. Requirement IDs are declared once; tests and provenance omit `requirement_id`. The framework derives these references from the containing entry, assembles the unchanged canonical `TaskSpec`/`RequirementsAnalysis`, and runs their strict validators. It does not invent missing requirements or rewrite IDs. Each functional/nonfunctional requirement has an observable success criterion, at least one executable test or manual-review test, and exactly one provenance record:

- `explicit`: a requirement stated in the request or supplied context.
- `inferred`: justified intent, with a rationale and supporting source quotation.
- `recommendation`: optional design advice; its requirement and all tests remain optional.

Traceability references exact substrings of the preserved request/context. Runtime and each technology constraint are separately traced as explicit, inferred or a declared framework default. `single_html` is the current default when technology/runtime is unspecified. Explicit incompatible needs are retained and flagged as unsupported rather than silently converted.

Missing information and unresolved ambiguities are separate lists containing questions, affected requirement IDs and blocking flags. Optional advice cannot become a mandatory test or generation blocker. Layout, DOM hierarchy, navigation and architecture remain implementation choices unless explicitly requested; any acceptance hooks should be minimal and layout-neutral.

The API JSON Schema is derived from Pydantic and constrains the original request to its exact input value. Supporting context appears once in the analyst's user payload and is excluded from the model response schema and output. The framework copies the exact authoritative context into the canonical task before validating provenance; the model cannot echo or replace it. This avoids duplicating entire documents as JSON Schema constants or generated output. Pydantic additionally checks source quotations, complete/nonduplicated requirement/constraint traceability, test coverage, optionality and issue references. It rejects disabled verification/accessibility. Unsupported schema requests, malformed output, unexpected wrappers and truncation fail without retries or semantic repair.

The complete response schema is sent through API `response_format` and recorded in `intake_request.json`, without a second full-schema copy in the user message. The message contains small field-name and browser-DSL allowlists derived from existing Pydantic models. Large evidence still consumes the loaded model's context window; if a request or its completion cannot fit, it fails explicitly without truncating documents, retrying, changing model placement or increasing the context setting automatically.

Source references use separate request/context schema alternatives. Each alternative restricts `quote` to exact excerpts from that source: whole short sources, nonblank lines split into at most 1,000-character excerpts, and individual whitespace-delimited words. Duplicate choices are removed. These choices are supplied only in the API schema, preserving the single evidence copy in the user message. A request quotation labelled as context (or the reverse) is rejected unless the same text genuinely occurs in both sources. The unchanged canonical validator still checks exact substrings independently. Historical canonical provenance remains readable; new model responses select from the constrained excerpt vocabulary. This prevents invalid quotation/source pairs but cannot prove that a quotation semantically supports an inference.

Requirement-specific missing-information and ambiguity entries are nested inside their requirement and omit `requirement_ids`; the framework derives that reference during canonical assembly. Top-level issues are global and use `requirement_ids=[]`. This prevents dangling issue references without repairing model outputs or inventing missing requirements. An issue affecting several requirements can be expressed as separate requirement-local issues with unique IDs or as a global issue when it affects the entire task. The saved canonical representation remains unchanged, including affected requirement IDs, blocker flags and strict issue validation.

The generated schema uses separate browser, universal and manual test variants. Browser/manual tests cannot carry universal checks; universal tests require checks and empty browser action/assertion lists. Manual requirements only accept manual tests, with no executable actions/assertions; executable requirements only accept browser/universal tests. Task-level tests and separate requirement traceability are prohibited in the model response, preventing independently generated requirement references. Saved canonical artifacts retain the original flat representation. Runtime has a required nested traceability object. Each technology constraint is a value/traceability object; the framework derives the flat canonical constraints, targets and indexes. Empty or duplicate standalone constraint-trace arrays cannot be generated because that field is absent from the response schema. Framework-default traces have no source citations, and context references are excluded when no supporting context was supplied. Framework metadata is not a user source. These constraints supplement the unchanged cross-reference and exact-quotation validators; they do not repair an invalid response.

## Artifacts and configuration

For `notice.json`, artifacts are created exclusively in `notice.intake/<timestamp>-<uuid>/` beside the manifest:

- `input.json`, `original_request.txt`, and optional `supporting_context.txt` preserve the sources.
- `model_config.json`, `intake_request.json`, `intake_raw.txt`, and `intake_metrics.json` retain inference configuration, exact response format, raw output, usage, timing and finish reason.
- `analysis.json` records analysis version `1.0`, source/task hashes, model configuration/metrics, provenance, questions, runtime support and readiness.
- `task.json` is a copy of the canonical manifest.
- `metadata.json` and the exclusive `ledger/requirements_analyst.json` follow the existing artifact conventions.
- Failed runs preserve validation errors, structured-output rejection diagnostics and error records for the stages reached.

The source hash is SHA-256 over the existing canonical JSON fingerprint of the original request and supporting context. The task hash uses the existing normalized task contract hash. Short, nonblank prompts are accepted without padding. Optional `supporting_context` is carried by the task schema into generation; absent context is omitted from serialization to preserve existing manifest hashes.

The analyst reuses planner inference settings: `--model`, `--base-url`, `--seed`, `--temperature`, `--top-p`, and optional `--max-tokens` (mapped to `planner_max_tokens`). Without a cap, the API omits `max_tokens`. Console progress uses stderr and the existing `--log-level`; final JSON uses stdout. No resource scheduling changes are introduced.

## Validation

The complete regression suite passed **185 tests and 115 subtests** in **70.78 seconds**, with one existing pytest collection warning. Forty-one focused A1 tests cover free-form analysis, explicit/inferred/optional classification, questions and blockers, exact source preservation, provenance, strict schema failures, independent JSON Schema validation of test/trace variants and source scope, archived intake failure rejection, optionality/verification guards, hash compatibility, immutable outputs, CLI configuration, both existing generation graphs, integrated collaborative routing/preview/stops, placement admission/owned cleanup and real Chromium execution of generated acceptance tests. Regression model responses are mocked. A separate live intake using google/gemma-4-e4b, seed 1025 and the exact portfolio request completed with finish_reason=stop in 22.85 seconds (5,109 prompt tokens, 2,180 completion tokens). Its five requirements and six tests compiled with valid references into tasks/generated/portfolio_test_nested_contract.json. The model selected manual review for every requirement and incorrectly classified the default runtime as user-specified; the result needs semantic review and its mandatory manual criteria remain unverified. The live artifacts are preserved separately from the archived failures. Five additional regressions cover that archived undeclared requirement, nested reference assembly, forbidden independent references, manual/executable alignment and canonical duplicate-ID rejection. The actual LangGraph development server also exposed the collaborative graph, its integrated Analyst node and the new input/output schemas successfully; the isolated validation server was stopped afterward.

## Limits

Schema/source checks cannot prove semantic completeness, correct classification, factual entailment or that a generated acceptance test fully captures the user's intent. Inspect the analysis, especially inferred obligations and criteria for open-ended design requests. Manual criteria remain unverified by the existing deterministic engine; missing content is not made up. Supporting text is accepted directly; A2 now also supplies locally converted document evidence through this same interface. See [A2.md](A2.md). Document conversion is outside the A1 analyst itself. Only the current single-HTML runtime can generate candidates. Backend/model JSON Schema support and analyst quality require model-specific testing; regression coverage uses mocked analysis responses and real Chromium for executable acceptance compatibility. The live Gemma check demonstrates valid schema generation, while its manual-test choices and runtime attribution demonstrate the limits of structural validation.

A1 includes no decomposition, variance conditioning, experiment matrices, batches, optimization or automatic repair.

Grounding validation: the repeated live failure quoted the original request but labelled it as context. The paired source/quotation schema rejects that mismatch. A subsequent live check exposed dangling issue IDs, addressed by requirement-local issues. The final live run completed with finish_reason=stop, 4,125 prompt tokens and 1,278 completion tokens, saving tasks/generated/personal_site_grounded_issues_check.json. Its original prompt and 10,034-byte supporting evidence match the archived input exactly. No archived response was repaired and no runtime retry was added. The full regression suite passed 235 tests and 157 subtests in 75.60 seconds, with one existing collection warning. Successful structural/provenance validation still requires human review of semantic coverage and inferred requirements.

Constraint-contract audit: runtime provenance is mandatory by construction, including when technology_constraints is empty. Recommendations can only appear in optional requirement variants; requirement-local optional issues cannot block generation. Tests omit required and inherit mandatory/optional status from their requirement. Verification/accessibility flags are constrained true. Browser action/assertion variants encode required values, allowed keys, nonnegative integer counts and nonblank accessible names/criteria. Static runtime variants require an entrypoint; web-app variants require an entrypoint or URL. Five new focused tests exercise independent JSON Schema and Pydantic rejection, provenance assembly and these adjacent consistency rules. The full suite passed 240 tests and 183 subtests in 83.44 seconds, with the existing collection warning. Canonical schemas and validation remain unchanged. Unique generated identifiers, aggregate test-count limits, local path/URL security checks and semantic entailment remain final validation responsibilities; structural schema constraints are not a guarantee of arbitrary model output quality.

Final live verification: the original intake command created tasks/generated/personal_site.json successfully at a verified LM Studio context_length of 32,768 (existing parallel=4 retained). The run finished normally with 4,171 prompt tokens and 4,206 completion tokens, producing 10 requirements and 12 tests. The original request and converted document evidence are unchanged; runtime/technology provenance and A3 companion-analysis discovery were verified. The output cap remains unset. The earlier 8k length-limited runs are preserved.

Issue identity: model responses omit issue_id in global and requirement-local missing-information/ambiguity entries. During canonical assembly, the framework assigns missing_001, missing_002, etc. and ambiguity_001, ambiguity_002, etc. in deterministic list order (global entries first, then nested requirement entries). Prefixes separate the two groups, so IDs are globally unique. Every description, question, quotation, scope and blocker flag is retained; repeated content is not deduplicated. Canonical IntakeIssue/RequirementsAnalysis schemas and historical IDs remain unchanged and continue to reject duplicated canonical IDs. A model-provided issue_id is a forbidden extra field, not a value silently renamed or repaired. IDs are stable for an identical response/frozen artifact, not promised stable across independently reordered analyses.
