# B1 — Reproducible experiment planning

B1 produces candidate manifests only. It does not invoke a graph, query LM Studio,
load models, generate sites, inject variance directives, or launch a browser.
The existing generation CLI, graphs, resource scheduler, acceptance authority,
canonical task files and historical artifacts remain unchanged.

## Commands

From `D:\generation-experiment` in the `agentic-web` environment:

```powershell
python -m agentic_web experiment plan `
  --config experiments/pilot.json

python -m agentic_web experiment plan `
  --config experiments/planning_1000.json
```

The checked-in pilot freezes `tasks/generated/personal_site.json` and its existing
`personal_site_tasks.json` decomposition. These are local research inputs, not
newly generated fixtures. If moving the configuration, also provide its referenced
frozen files. All relative paths (including output_root and variance profiles)
resolve from the configuration file's directory, not the process working directory.

The pilot crosses one task, two agent configurations, three variance labels,
three paired seeds, two temperatures and one top-p: **36 candidates**.
The scale example crosses one task, two configurations, two variance labels,
125 paired seeds, two temperatures and one top-p: **1,000 candidates**.
Both plans were created without executing any candidate.

The configurations demonstrate a Gemma baseline and a heterogeneous collaborative
configuration using Gemma, Ministral and Phi. Model families are explicit; parameter
counts, quantization and revisions are `null` (unknown), rather than guessed from
model names. This pilot varies workflow and model assignment together; it is not
a controlled attribution of differences to either factor alone. Create separate
named configurations holding other factors fixed for those comparisons.

## Configuration schema

`experiments/experiment.schema.json` is generated from the Pydantic
`ExperimentConfig` model. Extra keys and unknown schema versions are rejected.

| Field | Meaning |
| --- | --- |
| schema_version | `1.0` |
| experiment_id / experiment_version / description | Explicit experiment identity and purpose |
| output_root | Local directory for plans |
| tasks | Named frozen specification paths and verified hashes; optional paired decomposition path/hash |
| model_configurations | Named workflow, explicit role assignments and optional output-token limits |
| factors | Configuration names, temperatures, top_ps, seeds, variance_conditions, replicate count |
| planning | `full_factorial`, optional positive candidate_limit, deterministic selection_seed |

Baseline requires exactly Planner and Implementer. Collaborative requires exactly
Planner, Implementer, UX, Architect, Coordinator and QA. Each role specifies
`model`, optional `family`, `parameter_count` (positive integer number of parameters),
`quantization`, and `revision`. Missing metadata is serialized as null. Role names
are lowercase. Every used role must be explicit; no environment-dependent model
fallbacks become experimental factors. Optional `planner_max_tokens`,
`review_max_tokens` and `max_tokens` use the existing inference semantics; null
means no client output cap. Baseline cannot set a specialist review limit.

Variance entries have an `identifier` and optional paired `profile_path` /
`profile_hash`. Profiles are arbitrary local JSON, validated for hash equality and
referenced without copying their content into the plan. Labels are application
independent and are not restricted to the examples. B1 never interprets profiles
as instructions. The schema can already reference future B2 directives.

## Hashes, identities and reproducibility

Specification hashes use the existing `workflow.contract_hash` over the validated
TaskSpec. Decomposition hashes are A3 `structure_hash` values, verified through
`load_decomposition` including requirements, dependency graph, origins, blockers
and readiness. Neither uses raw file bytes, so JSON formatting changes are harmless.
Profiles and normalized configurations use the existing `provenance.fingerprint`
(SHA-256 of sorted-key JSON). Do not substitute a raw file checksum for these hashes.

Candidate IDs are `candidate-<64 hex SHA-256>` of a versioned effective identity:
experiment ID/version, frozen task/decomposition hashes, workflow, role models
and known revisions/quantization, token limits, temperature, top-p, seed, variance
identifier/profile hash, and one-based replicate number. No timestamps, paths,
configuration aliases or output directories enter candidate IDs. Family and
parameter count are descriptive metadata; they do not manufacture new candidates
for otherwise identical inference settings. Changing metadata still changes the
configuration hash. Object key ordering and factor list ordering do not change
candidate IDs. All candidate records are sorted by ID.

Duplicate levels, effective model aliases and identical frozen task inputs are
rejected. Intentional repeated attempts use `replicates`; they retain the same
sampling seed and are distinguished by replicate identity. A changed experiment
ID/version deliberately creates a new candidate namespace.

Seeds are paired across variance conditions in the full factorial. The base seed
and actual requested per-role seed are both recorded: existing inference offsets
are Planner +0, Implementer +1, UX +2, Architect +3, Coordinator +4, QA +5.
Every role receives the configured temperature/top-p without model-specific changes.
Reproducible planning does not promise deterministic inference from a backend.

When limited, the planner ranks candidates by SHA-256(selection_seed, candidate_id),
selects the requested count, then sorts by candidate ID. This is deterministic,
not stratified or guaranteed balanced. Marginal summaries show every requested
factor level, including zero counts; complete definitions permit joint coverage
inspection. A bounded subset may break seed pairing between conditions. Use the
full matrix when complete pairs are required. A limit above the factorial count
selects the full matrix. Enumeration is in memory and O(full factorial size);
the tested 1,000-candidate example does not imply unbounded-scale support.

## Artifacts and interfaces

```text
runs/experiments/
  resume-pilot-b1/experiment_plan.json
  resume-scale-b1/experiment_plan.json
```

Each plan contains `plan_schema_version`, `configuration_hash`, the normalized
`configuration`, `full_factorial_count`, `planned_candidate_count`,
`selection_method`, `factor_summary` and complete `candidates`. The saved file
also records `reference_base` for resolving relative input paths. That machine-local
locator is excluded from hashes and candidate IDs. No CV content, task text,
decomposition body, source documents or generated applications are embedded.

Counts and summaries print after all validation but before creating output.
Plan files are opened exclusively. Replanning identical content reuses the file
without writing it; any changed configuration or manifest at that destination is
rejected. Use a new experiment ID/output root for changed plans. Existing files
are never replaced. File validation is read-only and frozen hashes must be
rechecked by any future executor before inference, since references can later change.

Programmatic interfaces in `agentic_web.experiments`:

- `read_config(path)` validates configuration JSON.
- `expected_counts(config)` gives exact full and selected counts without I/O.
- `candidate_matrix(config)` is the pure enumeration/selection function.
- `build_plan(config, base)` validates referenced inputs and builds the manifest.
- `save_plan(plan, config_path)` performs the separate protected write.

Planning validates assignment completeness, not local model availability,
backend capabilities or hardware feasibility. Those remain execution concerns.
A frozen blocked/unsupported A3 artifact remains unchanged; including its reference
in an experimental matrix does not certify execution readiness or resolve blockers.
There is no `experiment run` or `experiment resume` command in B1. B2 can consume
variance labels/profile references but must separately implement their semantics.

## Validation

`tests/test_experiments.py` uses unittest conventions with local task/decomposition
fixtures and no LLM responses. It covers schema validation, exact counts, multiple
tasks and replicates, seed pairing/offsets, path/key-order-independent IDs,
duplicate rejection, metadata and token limits, hash mismatch/tampering, declarative
profiles, subset coverage, protected writes and CLI planning of 1,000 candidates.
Inference, model loading, hardware discovery, graph invocation and browser startup
are patched to raise during the CLI test.

Complete regression command: `python -m pytest -q`.
Result: **259 passed, 213 subtests passed, one existing PytestCollectionWarning**
about the Pydantic `TestCase` class, in **75.42 seconds**. B1 adds 16 tests and
26 subtests. Both saved example plans were replanned successfully and retained
identical bytes and modification times (36 and 1,000 unique candidate IDs).

`experiments/experiment.schema.json`, this document and the two plan artifacts.
