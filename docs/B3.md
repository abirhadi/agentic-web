# B3 — Sequential candidate batch execution

The executor consumes saved B1 plans and invokes the existing baseline or
collaborative generation graph once per selected candidate. Candidates execute
sequentially; the collaborative graph retains parallel UX/Architecture reviews.
Frozen A3 artifacts use the existing load/validation branch without decomposition
inference. A1/A2 are not invoked. No retry, resume, repair or scheduler policy is added.

## Commands

The new `experiments/executable_pilot.json` freezes the existing resume task and
decomposition and pins the B2 profiles. Its saved plan contains 36 candidates.
Historical B1 configurations and plans remain unchanged; their unbound non-control
labels are intentionally rejected for execution rather than silently assigned profiles.

```powershell
python -m agentic_web experiment plan `
  --config experiments/executable_pilot.json

python -m agentic_web experiment run `
  --plan runs/experiments/resume-executable-b3/experiment_plan.json `
  --max-candidates 3 `
  --dry-run

python -m agentic_web experiment run `
  --plan runs/experiments/resume-executable-b3/experiment_plan.json `
  --max-candidates 3 `
  --resource-config resources.local.json
```

The last command performs live generation when run by the user; it was **not run**
during implementation. The planning and three-candidate dry-run commands succeeded.
Dry-run validates frozen inputs and lists candidate IDs without creating an execution
directory, connecting to LM Studio, loading models or invoking graphs.

Omit `--max-candidates` to execute all candidates in saved plan order. The limit
selects the first N, not a newly sampled subset. Optional `--base-url` selects the
existing backend endpoint; optional `--resource-config` enables the existing
resource-aware scheduler. Neither changes candidate factors. Their effective
settings are recorded; model/sampling overrides are deliberately absent from B3.

## Validation and execution

The runner validates the saved plan by reconstructing it from its embedded B1
configuration and comparing the complete candidate matrix, order, counts, hashes
and metadata. It uses the recorded `reference_base` for relative input references.
All referenced task/decomposition hashes are validated. Every selected treatment
is validated using B2 before any execution directory or inference is created.

Before each candidate, the plan and frozen inputs are revalidated. ModelConfig is
constructed from the saved role assignments, temperature, top-p, base seed and
token limits. The existing role seed offsets remain in force. Frozen TaskSpec
content is passed unchanged. The profile reference is absolute with its B1 hash
pinned; the graph independently validates it and records exact treatment prompts.
No profile directive or sampling value is synthesized by the executor.

Each candidate gets a freshly built instance of the existing graph. Existing
normal-path cleanup remains authoritative. A minimal optional session observer in
`build_graph` lets the batch executor call the same idempotent ResourceSession.close
in a finally block after unexpected graph exceptions. This preserves ownership
rules and leaves unrelated resident models untouched. It introduces no new resource
placement or scheduling decisions.

Individual candidate failures are recorded and the loop continues. Changed frozen
inputs or a changed/invalid plan abort the batch. Validation also runs after a
completed candidate, retaining its record before an invariant failure aborts further
execution. As with existing file-based workflows, this is validation rather than
an operating-system lock against concurrent external edits; freeze experiment input
files for the duration of execution.

## Artifacts

```text
runs/experiments/resume-executable-b3/
  experiment_plan.json
  execution/
    batch_started.json
    batch_result.json
    candidate-<original B1 hash>/
      started.json
      result.json
      runs/<existing timestamp-UUID>/
        application/index.html
        task.json
        task_decomposition.json
        variance_context.json
        <existing prompts, metrics, verification, resource and ledger files>
```

The executor reserves `execution/` exclusively. If it already exists, execution
fails before running candidates, even if only a prefix was previously executed.
There is no B4 resume behavior. New files are created exclusively; generated sites
are referenced in records rather than duplicated. Generated-but-rejected artifacts
remain available for research.

`started.json` preserves the original candidate definition, frozen hashes, profile
reference, exact requested ModelConfig, per-role sampling, resource settings and
start timestamp. `result.json` adds end time, elapsed seconds, failure stage/error,
run-directory reference, artifact path/availability, generation completion,
verification status, deterministic acceptance, QA status, available per-agent
token/latency metrics and resource telemetry. Batch summaries list each candidate's
status and record location. Metrics remain null/absent when the existing inference
path cannot supply them; no costs or token usage are invented.

Execution statuses distinguish:

- `generation_completed_verification_passed`
- `generation_completed_verification_failed`
- `generation_incomplete` (including truncated generation)
- `model_inference_failure`
- `workflow_agent_failure`
- `resource_failure`

Artifact availability and verification results remain separate even for resource
or workflow failures. Advisory QA failure does not override deterministic acceptance.
Known backend/resource exception diagnostics are categorized; unknown errors retain
their full diagnostic text and use workflow-agent failure rather than an invented
root cause. Batch `completed` means the loop finished, not that every website passed.
CLI exit code is 0 for a valid dry-run or all-passing completed batch, 1 for candidate
failures or a mid-batch abort, and 2 for initial validation/destination errors.
