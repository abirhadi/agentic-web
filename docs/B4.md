# B4 — Checkpointing and idempotent resume

The B3 runner now supports recovery through the same sequential execution loop.
The saved B1 plan remains authoritative. Candidate identities, experimental
replicates, model assignments, sampling, variance guidance, graphs, verification
and scheduler policies are unchanged.

## Commands

```powershell
python -m agentic_web experiment resume `
  --plan runs/experiments/resume-executable-b3/experiment_plan.json `
  --resource-config resources.local.json

# Run at most three eligible new attempts in saved plan order:
python -m agentic_web experiment resume `
  --plan runs/experiments/resume-executable-b3/experiment_plan.json `
  --resource-config resources.local.json `
  --max-new-candidates 3

# Explicitly permit new attempts for interrupted candidates:
python -m agentic_web experiment resume `
  --plan runs/experiments/resume-executable-b3/experiment_plan.json `
  --resource-config resources.local.json `
  --retry-interrupted `
  --max-new-candidates 1
```

Add `--dry-run` to inspect eligibility and reconstructed progress without inference.
Optional `--base-url` and resource settings follow B3 behavior and are recorded per
attempt. `experiment run --max-candidates N` still selects the first N candidates
and rejects an existing execution destination. Resume selects up to N eligible
unstarted/interrupted candidates, counting retries against `--max-new-candidates`.
Without that limit it considers the full saved plan. It can also start a plan with
no prior execution directory. No live pilot was executed for B4.

## Progress authority and classification

`started.json` and `result.json` reconstruct progress; `progress.json` is a disposable
summary. Corrupt or stale progress summaries do not cause regeneration. Candidate
definitions, IDs, role sampling and requested model settings are checked against
the validated plan. Changed frozen tasks, decompositions, profile hashes, plan
content or conflicting candidate identities reject execution.

- **not_started**: no candidate attempt directory exists.
- **interrupted**: an attempt was reserved but has no valid terminal result,
  including incomplete JSON, missing records or a partial generated HTML file.
- **completed**: a valid terminal result records generation completion, including
  verification rejection. Artifact existence by itself never establishes completion.
- **failed**: a valid terminal result records no completed generation, including
  inference failure, incomplete generation, resource or agent failure.

Both completed and failed terminal candidates are skipped on ordinary resume and
with `--retry-interrupted`. That option permits only operational retries of
interrupted work. It never retries verification failures or ordinary model errors.
Terminal results must contain the expected structured fields, consistent artifact
and verification state, timestamps and owned run/artifact references. Result files
remain authoritative even if an artifact is later manually removed; resume does
not regenerate completed observations to replace lost files.

The original B3 root directory is attempt 1. Interrupted retries use:

```text
execution/
  batch_started.json                 # original, immutable
  batch_result.json                  # original B3 invocation, immutable
  progress.json                      # atomic, reconstructed whole-plan snapshot
  resume_result.json                 # atomic latest resume invocation summary
  candidate-<unchanged B1 ID>/
    started.json                     # original attempt, preserved
    result.json                      # original result if any, preserved
    runs/<original run>/...
    attempts/
      attempt-0002/
        started.json                 # attempt_number=2, operational_retry=true
        result.json
        runs/<new run>/...
```

Original partial files, invalid records and generated artifacts are never deleted
or overwritten. Retry directories and attempt records are created exclusively.
Retries do not change the planned candidate count, base seed or replicate identity.
Progress includes all attempt references and partial run-directory references.

## Durability and ownership

Started/result records are flushed and fsynced before proceeding. Progress updates
are written after reservation, at every completed candidate boundary, and during
normal exception or manual-interruption unwinding. Mutable summaries use a flushed,
fsynced same-directory temporary file and atomic `os.replace`. If summary replacement
fails, the previous summary remains intact and the candidate records can reconstruct
the current state. A torn terminal record is treated as interrupted, never repaired.

One persistent `.execution.lock` file beside the plan holds an OS-level exclusive
lock for the invocation. Windows uses `msvcrt.locking`; POSIX uses `flock`. Concurrent
writers fail immediately. The kernel releases ownership after process termination,
so a leftover lock file does not imply a live owner and is never deleted to steal
ownership. Dry-run also obtains this lock for a consistent read; it may create the
lock file but creates no execution directory. These are local filesystem locks,
not a distributed queue or network-filesystem coordination guarantee.

Existing idempotent resource cleanup runs when graph execution unwinds, including
KeyboardInterrupt. A forcibly killed process cannot execute Python cleanup: models
left resident by an abandoned process require inspection under the existing resource
ownership rules. B4 does not guess which external model instances are safe to unload,
nor does it resume an in-flight backend prediction. Explicit retry starts a separate
candidate workflow and preserves the abandoned attempt.

## Summaries and exit codes

The progress object contains total planned candidates; not_started, interrupted,
completed and failed counts; total execution attempts; generation-status and
verification-status distributions; `all_candidates_terminal`; and per-candidate
attempt, result, run and artifact references. The latest resume summary additionally
lists the candidates selected in that invocation and any abort diagnostic.

A completed invocation means the selected loop finished, not that the whole plan
finished or all sites passed. A bounded successful prefix may return exit 0 while
not_started candidates remain; inspect the explicit counts. Exit 1 reports an abort,
an interrupted candidate still pending, or a terminal failure/rejection anywhere in
the reconstructed experiment. Valid dry-run returns 0; initial validation/ownership
errors use the existing CLI error exit 2.

## Files, tests and limitations

Added `agentic_web/checkpoint.py`, `tests/test_checkpoint.py` and this report.
Modified `agentic_web/batch.py`, `agentic_web/__main__.py` and `README.md`.
Historical B1/B2/B3 plans and artifacts remain unchanged.

Mocked tests cover prefix/repeated resume, manual interruption and cleanup, explicit
retry with preservation, verification and inference failures as terminal observations,
invalid result handling, legacy B3 compatibility, corrupted summary reconstruction,
changed frozen-input rejection, a real competing subprocess lock followed by forced
termination, atomic replacement failure, a 36-candidate incremental experiment,
1,000-candidate progress reconstruction and CLI controls.

No partial graph state is resumed: explicit interrupted retry starts the existing
workflow afresh. There is no retry policy for terminal failures, distributed locking,
automatic artifact repair, or hard-crash model unloading. Inputs should remain frozen
during execution; validation does not lock input files against external edits. Do not
run an older B3 writer that lacks the new ownership lock alongside this version.
Filesystem/hardware power-loss guarantees remain platform-dependent despite fsync
and atomic replacement. Stopped after B4; the full pilot was not executed.

Validation results: focused B3/B4 suite **24 passed**. Full command
`python -m pytest -q`: **293 passed, 229 subtests passed**, with one existing
Pydantic TestCase collection warning, in **86.34 seconds**. B4 adds 11 tests.
