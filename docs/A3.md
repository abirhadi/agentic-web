# A3 — Frozen requirement-level task decomposition

A3 produces coarse development outcomes from a validated canonical `TaskSpec`, using the existing Planner model, LM Studio interface, schema-constrained response handling and resource admission. This is a separate inspectable artifact, not a candidate architecture or an alternative planning framework. The existing Planner still creates the candidate-specific implementation strategy.

Standalone preparation creates no website and does not rerun A1/A2:

```powershell
python -m agentic_web decompose `
  --task tasks/generated/personal_site.json `
  --output tasks/generated/personal_site_tasks.json `
  --model google/gemma-4-e4b `
  --seed 1025
```

The optional `--analysis <analysis.json>` supplies matching A1 provenance/blockers. When omitted, the command discovers a matching A1 record under the canonical file's adjacent `<stem>.intake/<run-id>/analysis.json`. Multiple matching records require explicit selection. A supplied analysis is validated using `RequirementsAnalysis`, including source quotations, then matched against the full canonical specification and its hash. Unsupported runtimes are detected with the existing runtime adapter registry, without adding any runtime.

For natural-language/document preparation through A1/A2 followed by A3:

```powershell
python -m agentic_web intake `
  --prompt "Generate a personal website from my resume." `
  --document resume.pdf `
  --output tasks/generated/personal_site.json `
  --decompose `
  --decomposition-output tasks/generated/personal_site_tasks.json `
  --model google/gemma-4-e4b
```

Without `--decomposition-output`, intake writes `<canonical-stem>.tasks.json`. A failed decomposition does not remove or edit the already prepared canonical specification or A1/A2 artifacts. Blocked A1 specifications can still produce a blocked decomposition for inspection, but cannot proceed to candidate planning.

Reuse the same frozen graph across independent candidates:

```powershell
python -m agentic_web generate `
  --task tasks/generated/personal_site.json `
  --decomposition tasks/generated/personal_site_tasks.json `
  --workflow collaborative `
  --model google/gemma-4-e4b `
  --output runs
```

`generate --decompose` instead prepares a new decomposition before candidate planning. Both baseline and collaborative graphs have an optional `task_decomposition` node. Existing invocations bypass it and preserve their inference calls. Decomposition is opt-in; this avoids changing existing experiments' model workloads. The Planner receives `task_decomposition` alongside the unchanged task, requirements and plan schema. Candidate runs copy it to `task_decomposition.json` and verify the specification hash and conditions before planning. No acceptance criteria or verifier behavior are changed.

LangGraph Studio/programmatic collaborative inputs support:

```json
{
  "prompt": "Generate a personal website from my resume.",
  "documents": ["resume.pdf"],
  "decompose": true,
  "analyze_only": true,
  "output_root": "runs"
}
```

Natural requests route through the existing Analyst and then decomposition. `analyze_only: true` inspects A1/A3 without candidate generation. For a frozen canonical input, use `task_path` or `task_spec` with `decompose_only: true`. Use `decomposition_path` to reuse an artifact, or `decomposition_output_file` to select a new output path. Existing manifest inputs never rerun A1/A2. Use fresh threads for independent Studio requests; existing LangGraph state persistence is unchanged.

Each development task contains:

```json
{
  "task_id": "section-navigation",
  "title": "Provide accessible navigation between major sections",
  "description": "Make the approved major sections reachable and identifiable.",
  "requirement_ids": ["section_access"],
  "completion_criteria": ["Each approved major section is reachable using a named keyboard-operable control."],
  "dependencies": [],
  "priority": "high",
  "required": true,
  "status": "ready"
}
```

This illustrative task assumes `section_access` actually exists in the approved manifest; application identifiers are never embedded in the implementation. Task IDs are descriptive model-generated identifiers, validated for uniqueness and frozen in the artifact. Reusing the artifact preserves them; independent inference is not guaranteed to reproduce identical task IDs or task grouping, even with the same seed.

Pydantic and deterministic checks enforce:

- Nonempty tasks, titles/descriptions and observable completion criteria; bounded task counts and valid identifiers.
- Manifest-derived requirement ID enums, unique task IDs, no duplicate/unknown requirement references and complete mandatory requirement coverage.
- Exact optionality: tasks reference either mandatory requirements or optional requirements, never a mixture. Mandatory tasks cannot depend on optional work. Optional requirements may remain undecomposed.
- Existing dependency targets, no duplicate dependency references, no cycles (including self-dependencies), and a stored dependency order.
- Authoritative source conditions: blocked/unsupported statuses are derived from A1 blockers and runtime support, then propagated through dependencies. The model cannot mark those conditions resolved.
- Matching canonical hash, source registry, task statuses, dependency order, semantic-structure hash and readiness when loading a frozen artifact. New contradictory analysis conditions reject reuse.

The artifact's `requirement_registry` records mandatory/optional classification, explicit/inferred/recommendation origins, blocker details and unsupported-runtime diagnostics. Original requirements remain authoritative. The task-decomposition instructions request outcomes rather than layout/DOM/framework choices and preserve the manifest's design freedom. The candidate Planner is explicitly told that this guidance is not an architectural prescription.

Artifacts are saved in a new `<output-stem>.decompose/<run-id>/` directory:

- `task.json`: originating canonical snapshot, unchanged.
- `model_config.json`, `decomposition_request.json`: selected Planner configuration and actual Pydantic-derived response schema.
- `decomposition_raw.txt`, `decomposition_metrics.json`: raw model response, requested model/cap/seed, reported model, usage, timing and finish reason.
- `decomposition.json` and the requested output file: versioned task structure, canonical hash, requirement registry, dependency order, structure hash, validated A1 metadata when available, model configuration, metrics and readiness.
- Validation/backend/error diagnostics, `metadata.json` and an exclusive `ledger/task_decomposition.json`; resource config/admission/inference/cleanup artifacts when scheduling is enabled.

No existing output is overwritten. Malformed responses, unsupported schema requests, unknown references, cycles, optionality violations and truncated/content-filtered generations fail without retries, downgrades or semantic repair. `--max-tokens` is optional and uses the existing Planner limit. `--resource-config` invokes the unchanged scheduler through a separate existing Planner-role session for decomposition, closed before candidate planning; this avoids consuming the candidate Planner's one-use inference lease. Manually loaded external models are preserved.

Limitations: frozen legacy manifests do not encode A1 origins or blockers themselves. When no validated A1 record is available, origins are `unspecified`, `provenance_available` is false, and missing facts cannot be reconstructed automatically. Provide the original A1 analysis record when applicable. Manual verification is not treated as proof of completion or automatically reclassified; the existing verifier still leaves manual criteria unverified. Semantic relevance, appropriate task granularity, completeness of model-written criteria and freedom from unrequested architectural prescriptions cannot be proven by DAG/schema checks. Inspect the decomposition before reusing it. No live model-quality claim is made by mocked regression tests.

A3 includes no additional agents, scheduling policies, runtimes, decomposition repair, variance conditioning, experiment matrices, batch execution, diversity scoring or prompt-optimization agent.
